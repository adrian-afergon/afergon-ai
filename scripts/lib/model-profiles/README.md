# Model Profiles Vertical

Product vertical for model profile storage, resolution, and lifecycle. Layers point inward: `domain/` holds behavior classes, `application/` holds use cases and ports, `infrastructure/` holds adapters and composition roots.

## P3 resolution and lifecycle (inactive capability)

- `domain/profile-resolution.ts` — `ProfileAssignments` (validated assignments via reused `StoredAssignment`, immutable `withModel`/`withAssignment`/`withClearedEffort`, `affectedPairs`/`affectedPairsForModel` before-after collection, `cleanupCoverageFor`, `raw`), `ProfileResolution` (configured vs resolved model/effort with independent sources `explicit-model | explicit-inherit | implicit-inherit | runtime-default` and `explicit | no-override`, plus first-class `resolvedEffort`), `ProfileDesiredState` (`active`/`no-active`). Effort is always agent-local; parent effort never propagates, so `effortSource` describes both the configured and the resolved effort — there is no inherited effort and therefore no duplicated artificial source field. Legacy strings keep existing model semantics and mean no effort override. Patches carrying neither their own `model` nor their own `reasoningEffort` are no-ops that never replace or create entries. Alias duplicates for one canonical agent remain a visible ambiguity error (existing policy; no winner is invented).
- Cleanup coverage is the complete reconciliation scope per the accepted contract: every supported agent the desired assignments do not satisfy (satisfied = desired carries a same-canonical entry AND the previous entry had no effort override or the desired entry carries one), unioned with PRIOR verbatim identities (previous-side foreign keys only). It applies to active desired states (including empty targets and switches from null/absent active profiles) and explicit no-active results; inactive operations, clones, and no-ops carry no coverage and no refresh intent. Destination-only foreign keys are not cleanup targets: they stay raw in the desired document, are never managed assignments, and never enter coverage. Prior-only identity strings stay opaque in coverage and are never forced into assignments; desired assignments list supported agents only (verbatim alias keys preserved).
- `application/profile-lifecycle-use-case.ts` — `ProfileLifecycleUseCase` with `saveAssignment`, `clearEffort`, `saveAssignments`, `cloneProfile`, `switchProfile`, `deleteProfile`; all return `Promise<LifecycleResult>`. The `ValidateAffectedPairs` port and the `AgentTargetPolicy` are required constructor-injected collaborators; there is no default acceptance. Rejections leave saved state and caller inputs untouched. Bulk items carry only `agentName` and `patch` against the one outer profile; an item with a different own `profileName` is rejected. All named-profile operations require the profile to exist — P3 never creates profiles implicitly (creation is `cloneProfile`'s explicit job).
- Commit sequence per operation: retain original source/document → version gate → independent candidate → mutate/resolve/collect → await pair validation → validate/recheck → snapshot the ORIGINAL source before any version-2 promotion (complete receipt required) → final validate/recheck → exactly one `atomicPersist`. Retained snapshots are recovery artifacts, not rollback garbage.
- Missing, unreadable, corrupt, malformed, and dangling states are errors, never intentional resets. Valid `activeProfile: null` is the only no-active source.
- `createProfileLifecycleCapabilities(env, validateAffectedPairs)` in `infrastructure/profile-composition.ts` is additive: the original `createProfileCapabilities` keyset and live routing are unchanged, and nothing reaches the lifecycle from CLI/TUI/facade entry routes before P8.
- Only the update and lifecycle application use cases may call `atomicPersist`; infrastructure and all other files are prohibited (asserted in `tests/model-profiles-architecture.test.ts`).

## P4 capability validation and pair-bound acknowledgements (inactive capability)

- `domain/capability-verdict.ts` — `CapabilityVerdict` with validated outcomes `supported | known-unsupported | unknown`, scoped provenance (provider, exact resolved model identity, transport, versioned evidence id, claim kind, pin) and model-specific feedback. Static validating factories; frozen instances.
- `domain/unknown-effort-acknowledgement.ts` — `UnknownEffortAcknowledgement` (versioned, assignment-local metadata under the `unknownEffortAck` own key; `resolved-pair` scope binds the exact model+effort, `runtime-default` scope binds the exact null model state + effort and is never a wildcard for future concrete models) plus `UnknownEffortAcknowledgementPolicy` (only unknown verdicts are authorizable; matching acknowledgements never bypass supported or known-unsupported evidence). Own-key reads treat prototype-carried payloads as absent; malformed/foreign payloads are inert and preserved; writes refuse foreign collisions; clearing effort removes valid owned metadata only.
- `application/capability-validation-port.ts` + `application/validate-profile-capability-use-case.ts` — per-pair explicit `EffortCapabilityContext` via an injected `CapabilityContextResolver` (no universal transport, no name inference; missing or mismatched context identity stays unknown), the shared strict validator returning one complete frozen receipt (including explicit `no-override` outcomes), and rejection of malformed/known-unsupported pairs before any acknowledgement applies.
- `application/profile-lifecycle-use-case.ts` — the P3 `ValidateAffectedPairs` port evolved additively: same readonly pairs, optional immutable per-request context, `Promise<void | CapabilityValidationReceipt>`. Trusted P3 void callbacks keep their exact behavior with no acknowledgement effects. The lifecycle captures independent candidate/stored-ack/context data before the await, verifies the WHOLE receipt (profile, agents, exact post-resolution pairs, complete coverage, no duplicates/unrequested entries) before applying anything, and persists acknowledgements in the same single atomic commit. Ordinary unchanged patches remain P3 no-ops; acknowledgement-only intent runs fresh validation and writes only when metadata actually changes; identical acknowledgements after fresh validation cause no write and no refresh; metadata changes can promote v1→v2 with the ORIGINAL source snapshotted first.
- `infrastructure/opencode-capability-evidence.ts` — immutable production seed for the candidate OpenCode 1.18.34 pin (commit `e9f8a210b9e2b1e13d375b84906069886eb3b767`): source-declared TEST CATALOG mapping for `openai/gpt-5.1` on `@ai-sdk/openai` with explicit effort options `none/low/medium/high`, recorded with JSON pointers and blob IDs. `infrastructure/opencode-capability-adapter.ts` classifies exact provider+identity+transport tuples; availability, resemblance, missing variants and out-of-menu values stay unknown. `infrastructure/opencode-compatibility-report.ts` reports the pin as source evidence and marks every untested version unverified.
- `createProfileCapabilityLifecycleCapabilities(env, resolver)` is additive: it injects exactly one strict validator into the P3 lifecycle factory and exposes the validator, adapter, report and evidence. Live CLI/TUI/install/update routes never reach it (asserted in the architecture tests).

### Limitations

- Source evidence is not execution: the pinned TEST CATALOG record is inspected source material. It claims neither executed schema acceptance, provider request acceptance, nor compatibility with any other OpenCode version. Task 006 owns the public configuration-boundary acceptance and instrumented request proof; task 011 records/reuses actual tested-version evidence.
- The production seed contains exactly one positive record. No negative production record is invented: known-unsupported classification is exercised only with clearly labeled unit-test negatives.
- The capability surface is unreachable from live effort controls at this task prefix; legacy model-only behavior is unchanged. A separate model-ID allowance never authorizes an unknown effort.
